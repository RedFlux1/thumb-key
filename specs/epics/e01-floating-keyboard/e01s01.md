# e01s01 — Overlay Window with Focus-Synced Lifecycle

**type:** feat
**risk:** P0
**context:** infra
**bcps:** 5

## §1 Business Narrative

Thumb-Key users on tablets, foldables, and landscape phones want the keyboard to
float above content instead of being locked to the bottom of the screen. This
story delivers the thinnest end-to-end path: a settings toggle that switches the
keyboard from a docked IME view to a floating overlay window that appears and
disappears with text field focus.

## §5 Main Flow

1. User opens Thumb-Key settings → Floating Mode section → toggles "Enable floating mode" ON
2. User taps any text field in any app
3. The keyboard appears as a floating overlay window (not docked at the bottom)
4. User types normally — the keyboard content is identical to the docked version
5. User taps outside the text field (focus leaves) → floating keyboard hides
6. User taps another text field → floating keyboard reappears

## §6 Alternative Flows

- **Overlay permission not granted:** Settings screen shows a prompt to grant "Draw over other apps" permission. Floating mode toggle is disabled until granted.
- **API < 26:** Floating mode is not available. Settings section explains why.
- **Toggle OFF while floating:** Keyboard immediately returns to docked mode. Next input session uses the normal IME window.
- **IME service destroyed (rotation, process kill):** Floating window cleaned up in onDestroy. Next onStartInput re-evaluates floating mode config and shows floating if enabled.

## §17 Gherkin Acceptance Criteria

```gherkin
Scenario: Enable floating mode via settings
  Given the user is in Thumb-Key settings
  When the user toggles "Enable floating mode" ON
  Then the FloatingModeConfig.enabled field is set to 1 in Room DB
  And the keyboard is hidden if currently showing (mode change takes effect next input session)

Scenario: Floating keyboard appears on text field focus
  Given floating mode is enabled
  When the user taps a text field in any app
  Then a floating overlay window containing the keyboard appears
  And the keyboard content matches the docked keyboard layout

Scenario: Floating keyboard hides on focus loss
  Given the floating keyboard is visible
  When the user taps outside the text field (focus lost)
  Then the floating overlay window is removed

Scenario: Floating keyboard reappears on next focus
  Given floating mode is enabled
  And the floating keyboard was previously shown and hidden
  When the user taps another text field
  Then the floating overlay window reappears

Scenario: Tap passes through outside the keyboard
  Given the floating keyboard is visible
  When the user taps on the app content (not on the keyboard)
  Then the touch is received by the app, not consumed by the floating window
  And the keyboard remains visible (unless focus was lost by the tap)

Scenario: Disable floating mode
  Given floating mode is enabled and the floating keyboard is visible
  When the user toggles "Enable floating mode" OFF in settings
  Then the floating window is removed
  And the next input session shows the normal docked keyboard

Scenario: Docked keyboard unaffected when floating disabled
  Given floating mode is disabled
  When the user taps a text field
  Then the normal docked keyboard appears at the bottom
  And all existing keyboard functionality works identically to before
```

## Steps

1. Add FloatingModeConfig Room entity, DAO, migration, and register in AppDb → verify: `./gradlew assembleDebug`
2. Add FloatingModeRepository (wraps DAO, exposes Flow<FloatingModeConfig?>) → verify: `./gradlew assembleDebug`
3. Add floating mode toggle to settings screen with overlay permission check → verify: `./gradlew assembleDebug`
4. IMEService: add showFloating(), hideFloating(), toggleFloatingMode(), isFloatingModeEnabled() → verify: `./gradlew assembleDebug`
5. IMEService: wire onStartInput → show floating if enabled; onFinishInput → hide floating → verify: `./gradlew assembleDebug`
6. ComposeKeyboardView: detect floating mode, wrap KeyboardScreen in Surface when floating → verify: `./gradlew assembleDebug`
7. Tap-through + zero content insets + fullscreen override → verify: `./gradlew assembleDebug`
8. Full preflight → verify: `./gradlew lintKotlin lint assembleDebug`

## Risks

- **IME lifecycle fights:** onStartInput/onFinishInput are the correct hooks, but Android OEMs (Samsung, Xiaomi) may fire them unpredictably. Mitigation: keep the implementation minimal — only show/hide in those two methods.
- **Overlay permission:** Some OEMs (Xiaomi, Huawei) make overlay permission hard to find or silently revoke it. Mitigation: check permission before enabling; show clear instructions if denied.
- **Memory leak:** WindowManager.addView without removeView on destroy will leak. Mitigation: always call hideFloating() in onDestroy.
