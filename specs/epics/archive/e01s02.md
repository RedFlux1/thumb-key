# e01s02 — Drag-to-Reposition and Position Persistence

**type:** feat
**risk:** P0
**context:** domain
**bcps:** 5

## §1 Business Narrative

With the floating overlay window working (e01s01), the keyboard currently appears
at a fixed position. Users need to move it to where it's comfortable — typically
higher up on large screens or to one side in landscape. They also expect that
position to survive orientation changes and reboots.

## §5 Main Flow

1. Floating keyboard is visible with a narrow drag handle bar at the top
2. User touches the drag handle and drags → keyboard follows the finger
3. Keyboard stops at screen edges (clamped to bounds)
4. User releases → position saved to Room DB for current orientation
5. User rotates device → keyboard loads the saved position for the new orientation (or default if never saved)
6. User flings downward (fast vertical swipe) on drag handle → floating mode disables, returns to docked

## §6 Alternative Flows

- **No saved position for this orientation:** Default to (100, 200) — a reasonable offset from top-left
- **User drags keyboard partially off-screen:** Clamped — x ∈ [0, screenWidth - keyboardWidth], y ∈ [0, screenHeight - keyboardHeight]
- **Drag ends but no velocity → reposition only:** Position saved, floating mode stays active
- **Fling down with low velocity:** Treated as drag-end (reposition), not dismiss. Threshold: 1000 px/s downward

## §17 Gherkin Acceptance Criteria

```gherkin
Scenario: Drag keyboard to new position
  Given the floating keyboard is visible
  When the user drags the handle by touch-and-move
  Then the floating window moves to follow the finger
  And the window is clamped to screen bounds

Scenario: Position saved on drag end
  Given the user dragged the floating keyboard to a new position
  When the user releases the drag
  Then the X and Y position is persisted to FloatingModeConfig in Room DB
  And the position is keyed by current orientation

Scenario: Position restored on next show
  Given a saved position exists for the current orientation
  When the floating keyboard is shown (via text field focus)
  Then the keyboard appears at the saved position

Scenario: Default position for unsaved orientation
  Given no saved position exists for the current orientation
  When the floating keyboard is shown
  Then the keyboard appears at a default position away from screen edges

Scenario: Orientation-specific positions
  Given a position saved in portrait mode
  When the user rotates to landscape
  And taps a text field
  Then the keyboard appears at the landscape-specific position (not the portrait position)
  And if no landscape position was ever saved, a default is used

Scenario: Fling down dismisses floating mode
  Given the floating keyboard is visible
  When the user flings the drag handle downward with velocity > 1000 px/s
  Then floating mode is disabled
  And the keyboard returns to docked mode for the next input session

Scenario: Slow drag down does not dismiss
  Given the floating keyboard is visible
  When the user drags the handle down slowly (velocity < 1000 px/s) and releases
  Then the keyboard is repositioned but floating mode remains active
```

## §18 Out of Scope

- Resize-from-corner handles
- Manual X/Y coordinate inputs in settings
- Snap-to-edge or snap-to-grid behavior
- Multi-touch or pinch-to-resize
- Position animation/spring physics on release

## Steps

1. Add drag handle composable (bar + DragHandle icon) above keyboard content, gated by isFloating → verify: `./gradlew assembleDebug`
2. Implement detectDragGestures with VelocityTracker for drag + fling detection → verify: `./gradlew assembleDebug`
3. Wire drag displacement to WindowManager.LayoutParams x/y, clamped to screen bounds → verify: `./gradlew assembleDebug`
4. Implement fling-down detection (velocity.y > 1000f → toggleFloatingMode off) → verify: `./gradlew assembleDebug`
5. Save position to FloatingModeConfig on drag end, keyed by orientation → verify: `./gradlew assembleDebug`
6. Restore position from FloatingModeConfig when creating floating window, with orientation-aware defaults → verify: `./gradlew assembleDebug`
7. Full preflight → verify: `./gradlew lintKotlin lint assembleDebug`

## Risks

- **Orientation detection during drag:** Rotation mid-drag could produce out-of-bounds positions. Mitigation: save position on drag end only (orientation is stable), and clamp on restore.
- **VelocityTracker accuracy:** Some devices report noisy touch data. Mitigation: use baseline threshold (1000 px/s) which is conservative enough for most hardware.
- **Window coordinates vs screen coordinates:** WindowManager.LayoutParams.x/y are relative to the gravity anchor (TOP|START). Mitigation: use TOP|START gravity consistently.
