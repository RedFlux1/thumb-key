# e01s03 — YAML Keybinding and Opacity Setting

**type:** feat
**risk:** P1
**context:** domain
**bcps:** 3

## §1 Business Narrative

Currently, the only way to toggle floating mode is through the settings screen.
Power users need a keyboard shortcut. Additionally, the floating keyboard is
fully opaque, which can be visually heavy — a user-adjustable opacity gives
them control over how much the keyboard blends with content behind it.

## §5 Main Flow

1. User configures a key (e.g., swipe-up on the spacebar) to `ToggleFloatingMode` via YAML or the key already exists in CommonKeys.kt
2. User presses the toggle key → floating mode toggles on/off immediately
3. If toggling on: current docked keyboard hides, floating overlay appears
4. If toggling off: floating window removed, docked keyboard restored
5. In settings → Floating Mode, user adjusts opacity slider (30%–100%)
6. Opacity change applied immediately to the floating window via `alpha` on WindowManager.LayoutParams

## §6 Alternative Flows

- **ToggleFloatingMode pressed while no text field focused:** Toggle state saved; takes effect on next focus
- **Opacity slider at 30% (minimum):** Keyboard remains readable but semi-transparent
- **YAML key modification for ToggleFloatingMode:** User writes `keyAction: ToggleFloatingMode` in key-modifications.yaml; parsed on next keyboard restart

## §17 Gherkin Acceptance Criteria

```gherkin
Scenario: Toggle floating mode via keypress
  Given the keyboard is docked and visible
  When the user presses the ToggleFloatingMode key
  Then floating mode is enabled
  And the floating overlay keyboard appears, replacing the docked keyboard

Scenario: Toggle floating mode off via keypress
  Given floating mode is enabled and the floating keyboard is visible
  When the user presses the ToggleFloatingMode key
  Then floating mode is disabled
  And the docked keyboard replaces the floating overlay

Scenario: ToggleFloatingMode via YAML key modification
  Given a key-modifications.yaml entry maps a key to ToggleFloatingMode
  When the keyboard starts and that key is pressed
  Then floating mode toggles on or off

Scenario: Opacity slider changes keyboard transparency
  Given floating mode is enabled and settings show the opacity slider
  When the user moves the slider to 50%
  Then the floating window alpha updates to 0.5
  And the change is persisted to FloatingModeConfig in Room DB

Scenario: Opacity applied on next floating window creation
  Given the opacity was saved as 40%
  When the floating keyboard appears (on text field focus)
  Then the floating window has alpha 0.4

Scenario: Opacity minimum at 30%
  Given the opacity slider
  When the user tries to set opacity below 30%
  Then the slider clamps to 30%
```

## §18 Out of Scope

- Opacity animation/transition on change
- Per-app opacity overrides
- Auto-dim when not typing
- Theme-dependent default opacity

## Steps

1. Add ToggleFloatingMode to KeyAction sealed class in Types.kt → verify: `./gradlew assembleDebug`
2. Handle ToggleFloatingMode in performKeyAction() → verify: `./gradlew assembleDebug`
3. Add ToggleFloatingMode deserialization in KeyboardModificationService.kt → verify: `./gradlew assembleDebug`
4. Add TOGGLE_FLOATING_MODE_KEYC convenience key to CommonKeys.kt → verify: `./gradlew assembleDebug`
5. Add opacity slider to floating mode settings (30–100 range), persist to Room → verify: `./gradlew assembleDebug`
6. Apply opacity from FloatingModeConfig when creating floating window in showFloating() → verify: `./gradlew assembleDebug`
7. Full preflight → verify: `./gradlew lintKotlin lint assembleDebug`

## Risks

- **KeyAction sealed class:** Adding a new variant requires updating ALL `when` branches in Utils.kt. Mitigation: Kotlin compiler enforces this — the build will fail if any branch is missed.
- **YAML deserialization ordering:** If the parser is order-sensitive, ToggleFloatingMode must be added in the right position. Mitigation: add a test case in the YAML test (if one exists) or verify manually.
- **Opacity on low-end devices:** Very low opacity (30%) may be unreadable on some screens. Mitigation: 30% minimum is a safe floor; user can always adjust up.
