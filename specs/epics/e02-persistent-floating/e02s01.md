# e02s01 — Persistent mode foundation: lifecycle independence

**type:** feat
**risk:** P0
**context:** infra
**bcps:** 5

## §1 Business Narrative

The current floating keyboard follows the standard IME lifecycle — it appears when a text field is focused and hides when focus is lost. This prevents using the keyboard like a hardware keyboard for navigation (arrows, Tab) and shortcuts (Ctrl+R, Ctrl+T) on web pages and apps that don't have a text field focused.

This story delivers the core plumbing: a persistent sub-mode of floating that keeps the keyboard visible regardless of text field focus, dismissible only by user action (fling-down on the drag handle). The DB schema, settings plumbing, IME lifecycle hooks, and dismiss gesture are all wired in this story.

## §5 Main Flow

1. User has floating mode enabled (already working from e01)
2. User opens Thumb-Key settings → Floating Mode → toggles "Keep keyboard visible" ON
3. User taps a text field in any app → floating keyboard appears as normal
4. User taps outside the text field (focus lost) → floating keyboard **stays visible** (new behavior)
5. User uses modifiers/shortcuts on web pages without a text field
6. User flings down on the drag handle → floating keyboard **hides** AND persistent mode is disabled

## §6 Alternative Flows

- **Persistent ON, floating OFF:** The persistent toggle is disabled/greyed out in settings when floating mode is off. Toggling floating OFF while persistent is ON disables persistent automatically.
- **Fling-down dismiss (persistent ON):** Fling-down triggers `hideFloating()`, sets persistent mode to 0 in DB, and calls `requestHideSelf(0)` to hide the IME. Next time the user focuses a text field, the keyboard appears in floating mode (persistent is off).
- **Fling-down dismiss (persistent OFF):** Same as current behavior — disables floating mode entirely, returns to docked.
- **IME process killed / rotation:** Floating keyboard cleaned up in onDestroy. Next onStartInput re-evaluates persistent config. If persistent was on, keyboard reappears on next text field focus (persistent does NOT auto-show — user must trigger IME).
- **Overlay permission missing:** Persistent mode checkbox is disabled with explanation text, same as floating mode toggle.

## Steps

1. Add `persistentFloatingEnabled` column to AppSettings entity + DEFAULT constant + DB migration → verify: `./gradlew assembleDebug`
2. Add `persistentFloatingEnabled` to OtherSettingsUpdate + wire through AppSettingsRepository.updateOtherSettings() → verify: `./gradlew assembleDebug`
3. Add `isPersistentFloatingEnabled()` to IMEService (guard: floating on + persistent setting true + API 26+) → verify: `./gradlew assembleDebug`
4. Modify `onWindowHidden()` — skip hideFloating() when persistent is on → verify: `./gradlew assembleDebug`
5. Modify `onFinishInput()` — skip hide behavior when persistent is on → verify: `./gradlew assembleDebug`
6. Modify `onEvaluateInputViewShown()` — return true when persistent is on → verify: `./gradlew assembleDebug`
7. Modify fling-down gesture in ComposeKeyboardView — when persistent on, hide IME + disable persistent; when persistent off, behave as before → verify: `./gradlew assembleDebug`
8. Full preflight → verify: `./gradlew lintKotlin lint assembleDebug`

## Risks

- **IME lifecycle fights:** Android OEMs (Samsung, Xiaomi, Huawei) may force-kill IME windows or fire lifecycle callbacks out of order. Mitigation: keep changes minimal — only add skip conditions in onWindowHidden/onFinishInput/onEvaluateInputViewShown, don't restructure the lifecycle.
- **Battery/perf watchdog:** Android may kill IME services that keep windows open too long. Mitigation: persistent mode is opt-in, user explicitly enables it. The keyboard still uses a lightweight overlay window.
- **Regression on non-persistent path:** Mitigation: all changes are guarded by `isPersistentFloatingEnabled()` — when false, code paths are identical to current behavior.
