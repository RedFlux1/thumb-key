# e02s02 — Key events without InputConnection: hardware keyboard parity

**type:** feat
**risk:** P0
**context:** domain
**bcps:** 5

## §1 Business Narrative

When persistent floating mode keeps the keyboard visible without a text field focused, the IME has no `InputConnection`. Currently, many key actions silently fail or are no-ops in this state because they depend on `currentInputConnection` being non-null.

This story makes all key actions work without an `InputConnection`: text characters are mapped to Android KeyEvents, modifier chords compose properly, navigation keys dispatch to the focused window, and mode toggles still affect keyboard state. The result is hardware-keyboard parity — the floating keyboard sends key events exactly like a physical keyboard would.

## §5 Main Flow

1. Persistent floating mode is enabled, keyboard is visible, no text field is focused
2. User presses `Ctrl+R` (via the Ctrl modifier key + R) → browser receives KEYCODE_R with META_CTRL_ON → browser refreshes
3. User presses `Tab` → focused window receives KEYCODE_TAB → focus moves to next element
4. User presses `Arrow Down` → page scrolls down
5. User presses letter `a` → focused window receives KEYCODE_A (may or may not have visible effect, same as hardware keyboard)
6. User types `Ctrl+C` (select text in browser, copy) → clipboard receives the operation
7. User focuses a text field (InputConnection becomes available) → CommitText works normally via InputConnection

## §6 Alternative Flows

- **InputConnection available:** When a text field IS focused, CommitText uses InputConnection.commitText() as before. No change to existing behavior.
- **Unmappable character:** For characters without a direct Android KEYCODE_* mapping, use KeyCharacterMap.getEvents() to convert. If that fails, log and silently skip.
- **Modifier chord with no InputConnection:** The modifier bitmask is applied to the KeyEvent's metaState. `Ctrl+C` sends KEYCODE_C with META_CTRL_ON in metaState.
- **Mode toggle actions (Shift, Ctrl, Alt, Meta, CapsLock, Numeric, Emoji, Clipboard):** These modify keyboard state or activeModifiers bitmask. They never need InputConnection and already work.
- **HideKeyboard action:** When persistent is on, HideKeyboard fling-downs as normal (hides IME and disables persistent). When persistent is off, behaves as before.

## §18 Out of Scope

- IME lifecycle independence (e02s01)
- Visual indicator (e02s03)
- Auto-show on boot
- Injection of key events via accessibility service or instrumentation (not needed — sendDownUpKeyEvents / sendKeyEvent are sufficient)
- Handling of non-ASCII Unicode characters without KEYCODE mappings

## Steps

1. Add null-safe guard in performKeyAction() — detect when `ime.currentInputConnection` is null → verify: `./gradlew assembleDebug`
2. Map CommitText characters to KeyEvents using KeyCharacterMap or manual KEYCODE_* mapping → verify: `./gradlew assembleDebug`
3. Apply activeModifiers bitmask to KeyEvent metaState for modifier chords without InputConnection → verify: `./gradlew assembleDebug`
4. Handle navigation/control keys (Enter, Backspace, Tab, Esc, arrows, Page Up/Down, Home, End, Delete, F-keys) through null-safe sendDownUpKeyEvents path → verify: `./gradlew assembleDebug`
5. Verify mode toggle actions (Shift, Ctrl, Alt, Meta, CapsLock, Numeric, Emoji, Clipboard) already work without InputConnection → verify: `./gradlew assembleDebug`
6. Full preflight + manual device verification → verify: `./gradlew lintKotlin lint assembleDebug`

## Risks

- **KeyCharacterMap reliability:** Different Android versions and OEMs may return different keycode mappings for certain characters. Mitigation: fall back to manual ASCII mapping for common characters (A-Z, 0-9, punctuation).
- **sendDownUpKeyEvents behavior:** This method has quirks on some OEMs (may not always deliver events to the correct window). Mitigation: test on multiple devices. If unreliable, fall back to `dispatchKeyEvent()` on the underlying decor view.
- **Meta state composition ordering:** Modifier bitmask must be applied before sending the key event, not after. Mitigation: apply activeModifiers to metaState at dispatch time, not at action-time.
- **Silent failures:** When InputConnection is null and key event dispatch fails, the user has no feedback. Mitigation: log failures at DEBUG level. No toast — too noisy for hardware keyboard use.
